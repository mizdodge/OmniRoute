#### Combo Builder Flow

The Combo Builder is a 5-stage wizard:

1. **Basics** — Name, description, strategy selection
2. **Steps** — Add model steps (provider/model/connection), combo-refs, provider-wildcards
3. **Strategy** — Select routing strategy (priority, weighted, round-robin, auto, lkgp, etc.)
4. **Intelligent** — Only shown for `auto` or `lkgp` strategies; configures intelligent routing
5. **Review** — Summary before save

**Stage gating**: `getComboBuilderStages()` returns all 5 stages for intelligent strategies, 4 stages otherwise. `canAccessComboBuilderStage()` enforces sequential completion.

**Draft state**: Stored in React state (`name`, `models[]`, `strategy`, `config`, `showAdvanced`, etc.) in `page.tsx`. The `config` object holds the intelligent routing configuration.

**Step storage**: `models` array holds `ComboBuilderDraftModelStep[]` — each entry has `{ model: string, providerId?: string, weight: number }`. These are normalized to `ComboStep[]` via `normalizeComboModels()` on save.

**Strategy storage**: Single string in `strategy` state (e.g., "priority", "auto", "lkgp").

**Intelligent Routing config**: Stored in `config` object, normalized via `normalizeIntelligentRoutingConfig()`. Contains:

- `candidatePool: string[]` — provider IDs to evaluate
- `explorationRate: number` — 0-1
- `modePack: string` — "ship-fast", "cost-saver", "quality-first", "offline-friendly"
- `budgetCap?: number`
- `weights: IntelligentRoutingWeights` — 13 factors
- `routerStrategy: string` — "rules", "cost", "latency", "sla-aware", "lkgp"
- `slaTargetP95Ms?, slaMaxErrorRate?, slaMaxCostPer1MTokens?, slaHardConstraints`

**Serialization**: On save, `normalizeComboModels()` converts draft steps to `ComboStep[]` with stable `id` fields. The full combo record (including `config`) is persisted via `createCombo()`/`updateCombo()` to the `combos` table (JSON in `data` column).

**Persistence**: `combos` table has `id`, `name`, `data` (JSON), `created_at`, `updated_at`. The `data` column stores the full combo including `models: ComboStep[]`, `strategy`, `config`, `version: 2`.

#### Combo Step Architecture

**`ComboModelStep`** (from `src/lib/combos/steps.ts`):

```typescript
{
  id: string;                    // Stable: "model-comboName-1-provider/model:connectionId"
  kind: "model";
  model: string;                 // Qualified: "provider/model"
  providerId?: string | null;    // Canonical provider ID
  connectionId?: string | null;  // Pinned connection, or null for auto
  allowedConnectionIds?: string[] | null;  // Account allowlist (#3266)
  weight: number;                // 0-100
  label?: string;                // Optional display label
  prompt?: string | null;        // Per-step pipeline input
  tags?: string[];               // Optional tags
  fallbackOnlyOnQuotaExhaustion?: boolean;
}
```

**Stable identifier**: The `id` field is generated by `buildStepId()` using `kind`, `comboName`, `index`, and a seed (model string + connectionId). This survives UI reordering but changes if the step is deleted and re-added.

**Signature for deduplication**: `getExactModelStepSignature()` produces `model:providerId:modelId:connectionId` (or `__auto__`). Used by `hasExactModelStepDuplicate()` to prevent duplicate steps.

**Combo-ref behavior**: Steps with `kind: "combo-ref"` reference another combo by name. Expanded at runtime via `resolveNestedComboTargets()`.

**Duplicate handling**: Exact duplicates (same provider/model/connection) are prevented at add-time. Different connections for same provider/model are allowed as separate steps.

#### Intelligent Routing Architecture

**`IntelligentRoutingConfig`** (from `src/lib/combos/intelligentRouting.ts`):

- `candidatePool: string[]` — Provider IDs to consider (empty = all active)
- `explorationRate: number` — 0-1, default 0.05
- `modePack: string` — One of 4 presets, default "ship-fast"
- `budgetCap?: number` — USD per request
- `weights: IntelligentRoutingWeights` — 13 factors summing to ~1.0
- `routerStrategy: string` — "rules" | "cost" | "latency" | "sla-aware" | "lkgp"
- `slaTargetP95Ms?, slaMaxErrorRate?, slaMaxCostPer1MTokens?, slaHardConstraints`

**Candidate Pool**: Built from active providers in `BuilderIntelligentStep.tsx` via `toProviderOptions()`. Can be restricted by user selection.

**Scoring Weights** (DEFAULT_INTELLIGENT_WEIGHTS):

- quota: 0.16, health: 0.20, costInv: 0.16, latencyInv: 0.12
- taskFit: 0.08, stability: 0.05, tierPriority: 0.05, tierAffinity: 0.05
- specificityMatch: 0.05, contextAffinity: 0.08, cacheAffinity: 0
- sessionAvailability: 0.05, resetWindowAffinity: 0

**Mode Packs**: 4 presets in `MODE_PACK_OPTIONS` that bias weights.

**Router Strategies**: 5 options in `ROUTER_STRATEGY_OPTIONS`.

**Runtime consumption**:

- Virtual auto-combos use `createVirtualAutoCombo()` → `createVirtualAutoComboFromPrepared()` which builds `autoConfig` with `candidatePool`, `weights`, `explorationRate`, `routerStrategy`.
- Combo routing uses `scoreAutoTargets()` in `autoStrategy.ts` which calls `calculateScore()` from `scoring.ts`.
- The `IntelligentRoutingConfig` is stored in combo's `config` field and also mirrored in `autoConfig` for auto-combos.

#### Future Fast Worker Pool

- **Purpose**: Preferred for low-complexity/high-volume tasks (simple Q&A, formatting, basic coding)
- **Optimization**: Speed/cost
- **Selection**: User picks **one or more** models from existing Combo Steps
- **Runtime behavior**: Acts as a routing pool for "simple" task types; existing Intelligent Routing scorer selects best eligible model within the pool

#### Future Strong Reasoning Pool

- **Purpose**: Preferred for difficult reasoning-heavy tasks (complex coding, debugging, planning, analysis)
- **Optimization**: Quality/reasoning capability
- **Selection**: User picks **one or more** models from existing Combo Steps
- **Runtime behavior**: Acts as a routing pool for "complex" task types; existing Intelligent Routing scorer selects best eligible model within the pool

#### Candidate Pool Interaction

1. **Both role pools guaranteed candidates?** Yes — they come from Combo Steps which are already in the candidate pool (or can be added to it).
2. **Other Combo Step models still participate?** Yes — models not in either pool still participate in normal scoring.
3. **Adaptive scoring ranks all Combo Steps?** Yes — all steps scored; role pool membership adds suitability factor.
4. **Role pool membership = score boost?** Yes — not a hard filter; existing Intelligent Routing scorer selects best within pool.
5. **Only one role pool configured?** Works — only that pool's suitability applies.
6. **Same step in both pools?** Allowed — model can serve both roles; suitability factors apply independently.
7. **Role references removed step?** Ignored at runtime (validation on save warns, but runtime degrades gracefully).
8. **Intra-role failover?** Yes — if preferred pool candidate fails, existing scorer selects next best from same pool.
9. **Cross-role failover?** Yes — if entire preferred pool exhausted, fall back to other role pool, then existing Combo fallback.
10. **Empty pools?** Handled safely — empty pool treated as no preference; falls back to normal scoring.

#### Adaptive Analysis Design Direction

**Signals to evaluate** (lightweight, deterministic first):

- Message count / token estimate → complexity proxy
- Tool count / tool types → tool complexity
- Presence of code blocks, stack traces → coding/debugging
- Request length, nested reasoning → reasoning complexity
- Context window utilization → context complexity

**Where to run**: In `handleChatCore()` or `handleSingleModelChat()` before scoring — have access to `body`, `model`, `provider`.

**Latency target**: <5ms (synchronous, no LLM calls).

**Feeding scoring**: Output `taskType` ("simple" | "complex" | "coding" | "debugging" | "planning" | "analysis") → maps to role preference.

**Failure degradation**: Default to "simple" (prefer Fast Worker) or neutral (no boost).

#### Scoring Integration Direction

**Conceptual**:

```
Final Score = Existing Intelligent Score + (Role Pool Suitability × Role Pool Weight)
```

**Implementation**:

1. Add `fastWorkerPoolSuitability`, `strongReasoningPoolSuitability` to `ScoringFactors`
2. Add `fastWorkerPoolWeight`, `strongReasoningPoolWeight` to `ScoringWeights` (default 0)
3. In `calculateFactors()` / `scoreAutoTargets()`, compute suitability:
   - If candidate.stepId in config.fastWorkerModelRefs → fastWorkerPoolSuitability = 1.0
   - If candidate.stepId in config.strongReasoningModelRefs → strongReasoningPoolSuitability = 1.0
   - Else 0
4. Task classification determines which role pool weight is active:
   - Simple task → apply fastWorkerPoolWeight
   - Complex task → apply strongReasoningPoolWeight

**Preserves existing behavior**: When weights are 0 (default), no change to current scoring.

#### Failure / Fallback Considerations

**Current behavior** (from `chat.ts`, `chatCore.ts`, `combo.ts`):

- Circuit breaker per provider (OPEN/HALF_OPEN/CLOSED)
- Connection cooldown per account (`rateLimitedUntil`)
- Model lockout per provider+connection+model
- Fallback strategies: priority, weighted, round-robin, etc.
- Quality validation with retry

**Adaptive feature must**:

- Reuse existing fallback — role boost doesn't bypass circuit breaker/cooldown
- If role-assigned model unavailable, fall back to next highest scored candidate
- Never hard-fail due to role assignment

#### Risks

1. **Step ID stability**: Step IDs change if step is deleted/re-added. Role references may break. Mitigation: Validate on save, degrade gracefully at runtime.
2. **Task classification accuracy**: Heuristic may misclassify. Mitigation: Start conservative (low weights), allow operator tuning.
3. **Scoring complexity**: Adding factors increases cognitive load. Mitigation: Default weights = 0, opt-in via mode packs.
4. **Combo-ref steps**: Role assignment to a combo-ref step is ambiguous. Mitigation: Only allow model steps for roles (validate in UI).
5. **Virtual auto-combos**: Don't have fixed steps. Mitigation: Role assignment only applies to user-created combos with explicit steps.

3. How to handle combo-ref steps in role assignment — disallow, or resolve to leaf models?
4. Should the UI show a warning when a role references a step that no longer exists?
5. Do we need a "neither" option (clear role assignment) in the dropdown?

### Phase 4 — Adaptive Analysis & Role-Aware Runtime Scoring

Status: Completed

#### Implemented

- Reused the existing synchronous multilingual intent classifier already executed by the Auto
  strategy, avoiding a second prompt-analysis pipeline or an LLM classification call.
- Added deterministic adaptive task classification:
  - `simple` intent without complex request signals prefers the Fast Worker pool.
  - `math` and `reasoning` intents prefer the Strong Reasoning pool.
  - Coding requests split into light, heavy, and neutral signals instead of always selecting Strong.
  - Explicit tool choice or an extracted request of at least 2,000 tokens promotes an otherwise
    ambiguous new request to Strong Reasoning.
  - Ordinary `medium` requests accumulate enough Fast evidence to avoid an unnecessary AI call;
    low-confidence or conflicting requests such as undecided creative work remain neutral.
- Added Fast Worker and Strong Reasoning suitability factors to the existing Auto-Combo scorer.
  They default to zero and therefore do not affect Combos without an active role preference.
- Added runtime role-weight activation that reserves a conservative portion of the existing
  normalized scoring distribution instead of increasing the total above 1.0.
- Integrated mode-pack bias: Ship Fast has the strongest Fast Worker bias, Quality First has the
  strongest Strong Reasoning bias, and Cost Saver moderately favors Fast Worker requests.
- Applied membership by stable Combo Step ID after quota/eligibility filtering. A role assignment
  cannot restore an unavailable candidate.
- Wired role-aware weights into both primary rules-engine selection and fallback scoring. The
  engine does not reapply a mode pack over the already-adjusted weights.
- Added finite cross-role fallback ordering: remaining preferred-role targets, alternate-role
  targets, then unassigned/ordinary candidates, deduplicated by execution key.
- Preserved explicit non-rules router selection as the primary authority while still using the
  adaptive role chain for its fallback tail.
